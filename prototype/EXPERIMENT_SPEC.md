# Спецификация экспериментального стенда

## 1. Исследовательский вопрос

Сравниваются две стратегии выбора точки инъекции отказа:

1. случайный выбор из полного каталога точек;
2. выбор только из точек, которые присутствуют в трассе контрольного запуска.

Механизм активации отказа, набор типов отказов и бюджет запусков для обеих стратегий одинаковы. Это позволяет связать различия в результатах именно со способом выбора точки.

## 2. Сквозной сценарий

Единицей эксперимента является выполнение операции `Создать и оплатить заказ`.

1. Клиент отправляет запрос в `order-service`.
2. `order-service` создаёт заказ со статусом `PENDING` в PostgreSQL.
3. `order-service` вызывает `payment-service` по HTTP.
4. `payment-service` сохраняет платёж и возвращает успешный ответ.
5. `order-service` меняет статус заказа на `PAID`.
6. `order-service` публикует событие `order.paid` в Kafka.
7. `notification-service` получает событие и регистрирует отправку уведомления.

Для каждого запуска используется новый `order_id`. После серии экспериментов состояние PostgreSQL и Kafka восстанавливается из одной исходной точки.

## 3. Состав стенда

- `order-service` — входная точка сценария, хранение заказа, вызов платежа и публикация события;
- `payment-service` — создание платежа;
- `notification-service` — обработка события из Kafka;
- PostgreSQL — данные заказов, платежей и зарегистрированных уведомлений;
- Kafka — доставка события `order.paid`;
- OpenTelemetry Collector и Jaeger — сбор и просмотр трасс.

Сервисы реализуются на Python. Стенд запускается через Docker Compose.

## 4. Проверяемые инварианты

После каждого запуска автоматическая проверка оценивает следующие условия.

| Код | Инвариант |
|---|---|
| `I1` | Для одного `order_id` создано не более одного платежа. |
| `I2` | Если заказ имеет статус `PAID`, событие `order.paid` существует в журнале публикаций. |
| `I3` | Запрос завершается не позднее установленного тайм-аута успешным ответом или контролируемой ошибкой. |
| `I4` | Число повторных попыток не превышает заданный предел, а постоянные ошибки не повторяются. |
| `I5` | Для одного заказа зарегистрировано не более одного уведомления. |

Нарушение инварианта считается обнаружением дефекта. Обычный код ответа сервиса без нарушения инварианта сам по себе дефектом не считается.

## 5. Заранее внесённые дефекты

| Код | Дефект | Условие проявления | Нарушаемый инвариант |
|---|---|---|---|
| `B1` | Повторный платёж после потери успешного ответа | Платёж создан, но ответ `payment-service` не доходит до `order-service`; запрос выполняется повторно без ключа идемпотентности | `I1` |
| `B2` | Некорректные повторные попытки | `order-service` повторяет постоянную ошибку либо превышает лимит попыток | `I4` |
| `B3` | Потеря события после фиксации заказа | Статус `PAID` зафиксирован в PostgreSQL, затем публикация в Kafka завершается ошибкой; механизма outbox нет | `I2` |
| `B4` | Зависание при недоступности платежного сервиса | HTTP-клиент ожидает ответ без корректного тайм-аута | `I3` |

Каждый дефект включается отдельным флагом. Это позволяет проверять его изолированно и однозначно связывать нарушение инварианта с известной причиной.

## 6. Каталог точек и отказов

Каждая точка имеет стабильный идентификатор, например:

- `order.http.payment.create`;
- `order.db.status.commit`;
- `order.kafka.order_paid.publish`;
- `notification.kafka.order_paid.consume`;
- `payment.db.payment.commit`.

Полный каталог также содержит точки операций, которые не выполняются в основном сценарии: чтение заказа, возврат платежа, повторная отправка уведомления и служебные обработчики. Благодаря этому случайная стратегия может выбрать точку, не затронутую текущим запросом, а стратегия по трассе исключит её.

На первом этапе используются четыре типа отказов:

- задержка;
- недоступность или разрыв соединения;
- возврат ошибки;
- потеря ответа после выполнения операции.

Совместимость точки и типа отказа задаётся в каталоге. Обе стратегии используют один и тот же каталог.

## 7. Формат одного эксперимента

В журнал запуска записываются:

- идентификатор серии и номер запуска;
- стратегия выбора;
- случайное зерно;
- выбранная точка и тип отказа;
- параметры активации отказа;
- идентификатор трассы;
- время начала и окончания;
- результат проверки каждого инварианта;
- обнаруженный дефект;
- длительность запуска и служебные ошибки.

Сохранённой записи должно быть достаточно для повторного выполнения того же эксперимента.

## 8. Первый реализуемый результат

Первая версия стенда считается готовой, когда:

1. три сервиса и инфраструктура запускаются одной командой;
2. контрольный сценарий выполняется без инъекций;
3. все пять инвариантов проходят автоматическую проверку;
4. в Jaeger видна одна полная трасса от запроса до обработки события;
5. состояние стенда можно сбросить и повторить запуск с тем же результатом.

Только после этого добавляются дефекты и механизм инъекции. Такой порядок отделяет ошибки стенда от ошибок, которые должны обнаруживать экспериментальные стратегии.
