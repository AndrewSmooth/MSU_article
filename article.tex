  {\bfseries\MakeUppercase{Исследование методов управляемой инъекции отказов для тестирования отказоустойчивости распределённых приложений}}
\end{center}

\noindent\textbf{Аннотация.}
В работе сравниваются два способа выбора места для инъекции отказа. В первом случае сервис или взаимодействие выбирается случайно. Во втором используются данные трассировки: отказ вводится только в компоненты и связи, участвовавшие в выполнении тестового сценария. Эксперимент должен показать, позволяет ли второй способ быстрее находить заложенные дефекты. На стенде с PostgreSQL и Kafka оцениваются число найденных дефектов, число запусков до их обнаружения, воспроизводимость и накладные расходы.

\noindent\textbf{Ключевые слова:}
инъекция отказов; распределённые приложения; отказоустойчивость; трассировка; граф вызовов; тестирование.

\noindent\textbf{Abstract.}
The study compares two ways of selecting a fault injection point. The first selects a service or interaction at random. The second uses tracing data and injects faults only into components and connections involved in the test scenario. The experiment evaluates whether the second method detects seeded defects faster. The PostgreSQL and Kafka testbed is assessed by the number of detected defects, the number of runs required for detection, reproducibility, and runtime overhead.

\noindent\textbf{Keywords:}
fault injection; distributed applications; resilience; tracing; call graph; testing.
\end{english}

\section{Введение}

Эксперимент по инъекции отказа задаётся точкой воздействия, типом сбоя и моментом его активации \cite{basiri2016}. Если выбранный компонент не участвует в проверяемом сценарии, запуск заканчивается так же, как контрольный, и почти не даёт сведений об отказоустойчивости системы. При случайном выборе такие запуски неизбежны: множество настроенных компонентов и связей шире пути, который фактически проходит запрос.

Распределённая трассировка даёт другой способ сформировать множество кандидатов. Из завершённых трасс можно восстановить граф вызовов и оставить в нём только узлы и связи, наблюдавшиеся при выполнении сценария. У этого подхода есть цена: сбор трасс создаёт нагрузку, а полученный граф не содержит редко выполняемых ветвей. Поэтому преимущество такой стратегии нельзя считать заранее установленным.

\section{Цель исследования}

Цель работы --- экспериментально сравнить случайный выбор точек инъекции с выбором по фактическому графу вызовов. Проверяемая гипотеза $H_1$ состоит в том, что при одинаковом бюджете запусков стратегия, использующая граф вызовов, обнаруживает внедрённые дефекты быстрее случайной. Нулевая гипотеза $H_0$ предполагает, что различия между стратегиями укладываются в случайный разброс результатов. За один эксперимент принимается выполнение фиксированного пользовательского сценария при одной активной инъекции.

\section{Материалы и методы}

Стенд включает прикладные сервисы, PostgreSQL и Kafka. Перед началом серии его состояние восстанавливается из одной и той же исходной точки. Каждый запуск воспроизводит одинаковый пользовательский сценарий; меняются только место инъекции, тип сбоя и случайное зерно стратегии выбора. Параметры запуска и результат проверки сохраняются в журнале эксперимента.

В реализацию заранее вносятся четыре дефекта. Первый приводит к повторному побочному эффекту, когда ответ теряется после успешного выполнения операции. Второй проявляется при некорректных повторных попытках. Третий связан с потерей события после фиксации транзакции в базе данных. Четвёртый вызывает зависание запроса при недоступности нижестоящего сервиса. Такой набор даёт известную разметку: для каждого запуска можно установить, какой дефект мог проявиться и был ли он обнаружен проверкой.

Сравниваются две стратегии:

\begin{enumerate}[label=\arabic*.,leftmargin=*]
  \item Случайная стратегия выбирает компонент или взаимодействие из полного каталога доступных точек, после чего выбирает совместимый тип отказа;
  \item Стратегия по графу вызовов использует тот же каталог отказов, но исключает компоненты и связи, которые не встретились в контрольных трассировках сценария.
\end{enumerate}

Обе стратегии получают одинаковое число запусков. Порядок экспериментов задаётся заранее сохранёнными случайными зернами, поэтому серию можно повторить. Инъекция считается полезной, если она изменила наблюдаемое поведение системы: нарушила проверяемый инвариант, привела к ошибке запроса или изменила состояние данных. Для каждой стратегии доля таких запусков вычисляется по формуле

\begin{equation}
  \text{Д}_{\text{полезн}} = \frac{N_{\text{полезн}}}{N_{\text{всего}}},
\end{equation}

где $N_{\text{полезн}}$ --- число полезных инъекций, а $N_{\text{всего}}$ --- общее число запусков стратегии. Кроме доли полезных инъекций, фиксируются число найденных уникальных дефектов, номер запуска и время первого обнаружения каждого дефекта. Воспроизводимость оценивается повторным запуском сохранённой конфигурации. Накладные расходы вычисляются относительно контрольной серии без трассировки и инъекции.

Граф вызовов строится по контрольным запускам и потому отражает только выполненные ветви. Если редкая ветвь не попала в трассы, стратегия по графу не выберет расположенную в ней точку отказа. Случайная стратегия сохраняет шанс выбрать такую точку, если она присутствует в полном каталоге. Полнота исходных трассировок, таким образом, непосредственно влияет на сравнение.

Известный набор внедрённых дефектов упрощает проверку результатов, но ограничивает переносимость выводов. Эксперимент покажет эффективность поиска именно на выбранном стенде и сценарии; по нему нельзя оценить распространённость этих дефектов в промышленных системах. Отдельно следует учитывать прогрев сервисов, состояние брокера и базы данных между запусками. Эти факторы контролируются восстановлением исходного состояния и случайным чередованием стратегий.
